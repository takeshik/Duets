# ADR-54: Independent Snapshot Versioning for NuGet Packages

## Status

Accepted — partially supersedes [ADR-23](23_ci-and-package-publishing.md) (snapshot version production and package
selection) and [ADR-48](48_extract-duets-pad-into-its-own-package.md) (solution-wide snapshot packing)

## Context

The repository publishes four packages with explicit dependency boundaries: `Duets`, `Duets.Jint`, `Duets.Pad`,
and `HttpHarker`. ADR-23 originally applied one repository-wide NBGV height to every package and packed all of them
on every push to `main`.

That policy makes an unrelated commit advance every snapshot version. It also creates an inconsistent dependency
graph when only part of a package set is available in a feed: a newly packed dependent package can require the new
repository-wide version of a dependency even though that dependency did not change. Installing an older direct
reference alongside that dependent package then produces a NuGet package-downgrade error.

Stable releases do not have this problem. A release tag intentionally publishes the complete package set at one
explicit version such as `1.2.3`, so every project reference can resolve to the same release version atomically.

## Decision Drivers

- A snapshot version must advance only when the package's own build inputs change.
- A package boundary must remain useful inside the single repository; extracting packages into separate repositories
  is not required for independent snapshot versions.
- Project references must continue to become ordinary NuGet dependencies with versions generated by the referenced
  projects.
- A package artifact must remain traceable to its exact source commit without putting a commit identifier in its
  NuGet version.
- Stable releases must continue to publish all packages at one explicit tag version.

## Considered Alternatives

### A: Keep one repository-wide snapshot version

- Pro: The workflow can continue packing the entire solution on every push.
- Con: Unrelated packages receive new versions and dependencies on those artificial versions.
- Con: Partial feed availability can produce package-downgrade and missing-package restore failures.

### B: Assign independent snapshot heights within the existing repository

- Pro: NBGV `pathFilters` derive each package's height from its actual build inputs while preserving one solution and
  atomic cross-package changes.
- Pro: Existing `ProjectReference` items continue producing correct NuGet dependency versions during packing.
- Con: The publishing workflow must select only the packages whose filtered inputs changed.

### C: Maintain package versions manually

- Pro: Every version change is explicit.
- Con: Manual increments are easy to omit and duplicate information already present in Git history.

### D: Move each package to a separate repository

- Pro: Repository history would provide independent heights without path filtering.
- Con: Cross-package work would lose the current atomic build, test, and commit boundary without solving a source-code
  architecture problem.

## Decision

Choose alternative B for development snapshots while retaining synchronized stable releases.

Each packable project inherits the root `0.1-dev.{height}` NBGV version and defines `pathFilters` for:

- its own project directory, including its `packages.lock.json`;
- `src/shared`, whose source files are compiled into every package;
- the root version, common build, SDK, and signing-key files that affect every package.

The `main` branch is a public release ref for NBGV formatting purposes. This removes the automatic `g{commit}` suffix
from the NuGet version but does not remove the `-dev` prerelease identifier. Commit identity remains in the generated
assembly informational version and package repository metadata.

On a push to `main`, the publishing workflow compares the pushed range and packs only projects whose filtered inputs
changed. A dependency-only change does not repack its unchanged dependents: an existing dependent package retains its
older minimum dependency version, and a newer compatible dependency satisfies that range. When the dependent package
later changes, packing resolves each `ProjectReference` to the referenced project's current snapshot version.

On an exact `v{major}.{minor}.{patch}` tag, the workflow builds and packs all four projects with the tag version. A
post-NBGV build target replaces the development version properties while retaining the commit metadata calculated by
NBGV, so package and assembly versions are consistent with the stable release.

The workflow must not publish a newly packed artifact under an unchanged package ID and version from a different
commit. This preserves a single authoritative package-version-to-commit mapping.

## Rationale

Path-filtered heights express the existing package boundaries without introducing a second version database or a
repository split. NuGet dependency lower bounds already provide the needed behavior: a package only needs to require
the dependency version against which that package was built, not every later version of that dependency. Selective
packing is therefore both sufficient and necessary to keep package identity stable when its inputs did not change.

Stable tags remain synchronized because they represent an intentional repository-wide release rather than ongoing
snapshot history. Keeping these two policies separate addresses the development-only failure without weakening the
atomic stable release process.

## Consequences

- **Positive**:
  - Changes to `HttpHarker`, `Duets`, `Duets.Jint`, or `Duets.Pad` no longer advance unrelated snapshot package
    versions.
  - Package restore no longer requires an unpublished synchronized version of an unchanged package.
  - NuGet versions stay short while nupkg and assembly metadata retain exact commit traceability.
  - Stable releases remain a synchronized four-package set.
- **Negative / trade-offs**:
  - Snapshot version numbers are meaningful only together with the package ID; equal heights across different package
    IDs do not identify the same commit.
  - The NBGV path filters and workflow change-selection paths must remain aligned when common build inputs move.
  - Rewriting published Git history can still reuse a filtered height and is incompatible with immutable package
    publication.
