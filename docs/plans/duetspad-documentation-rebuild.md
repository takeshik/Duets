# DuetsPad 文書再構築計画

## この計画の用途

この文書は、過去の会話を持たない初期状態のエージェントへ、そのまま渡して実行させるための計画である。
この文書に書かれていない過去の合意、レビュー、作業経緯を知っていることを前提にしない。

作業の目的は、現在の未コミット文書移行を破棄し、指定した `HEAD` から文書を白紙で再構築することである。
再構築では、`HEAD` に存在する ADR とソースコードだけを正本とする。既存文書はリポジトリ外へ退避し、
新文書を執筆した後の欠落確認にだけ使用する。

この計画は作業指示であり、完成成果物ではない。利用者からこの計画の実行を指示された場合に限って実行する。
コミットは行わない。

## 目的

DuetsPad の規模に見合うように、現行状態を説明する文書を関心事ごとに分割する。人間の保守担当者と
AI エージェントの双方が、巨大な単一文書や DuetsPad の全ソースを読み込まずに、必要な契約、状態所有、
寿命、ブラウザー側の不変条件へ到達できるようにする。

再構築した文書は、次の条件を満たさなければならない。

- ADR とソースコードから確認できる現在の挙動だけを記載する。
- 一つの宣言や一つのソースファイルからは得られない、複数箇所にまたがる契約を記載する。
- IDE、XML 文書、TypeScript 宣言から得られる API 一覧、メンバー一覧、オプション一覧、既定値を転記しない。
- 既存文書にあった実質的な情報を、維持、言い換え、移転、宣言への委譲、または根拠付きの除外のいずれかで
  処理し、情報の処遇を不明なまま残さない。
- 各契約の詳細を一つの文書だけが所有し、他の文書は短い説明とリンクだけを持つ。

文章、見出し、順序、長さを旧文書と一致させる必要はない。欠落の有無は意味単位で判定する。

## 正本と補助資料

### 正本

正本は、基準コミットに含まれる次の二つだけである。

1. `docs/decisions/` にある `Accepted` ADR
2. ソースコード。C# の XML 文書、TypeScript 宣言、埋め込みブラウザー資源を含む

テストは、ソースコードの挙動を確認し、文書に書いた保証が自動検証されているかを判定するための証拠として使う。
テスト自体を新しい設計判断の正本にはしない。

### 補助資料

基準コミットにある既存文書は、新文書を完成させた後の欠落確認にだけ使う。既存文書の記述を、新文書の
正しさの根拠にはしない。

破棄対象となる現在の未コミット文書案は、正本にも補助資料にも使わない。そこから文章、表、判断を移植しない。

### 不一致の扱い

`Accepted` ADR とソースコードが食い違う場合、どちらかを暗黙に採用してはならない。不一致、関係する ADR、
ソース箇所、影響する文書を記録して作業を停止し、利用者の判断を求める。

既存文書の記述が ADR とソースコードの双方から確認できない場合も、推測で残してはならない。根拠付きで除外できる
場合を除き、利用者の判断を求める。

## 文書構造

現行状態を説明する中央文書は、次の配置とする。

```text
docs/<category>/<module>/...
```

- `<category>` は文書の種類である。
- `<module>` は `src/` 直下の csproj ディレクトリ名をそのまま使う。DuetsPad は `Duets.Pad` とする。
- 複数モジュールにまたがる文書では、モジュール階層を省略する。
- `docs/decisions/` は例外としてモジュール分割せず、全体で連番となる平坦な ADR 集合を維持する。
- `index.md` は自分のディレクトリだけを索引する。カテゴリをまたぐ入口には使わない。
- 空ディレクトリや、中身のない文書を対称性のために作らない。

今回使用するカテゴリは次の二つだけである。

| カテゴリ | 所有する内容 |
|---|---|
| `architecture` | 現在の責務境界、状態所有、寿命、並行処理、不変条件、主要な流れ |
| `reference` | 外部から観測できる契約。通信形式、HTTP 状態コード、エラー、順序、復旧、設定間の制約 |

`src/<Module>/README.md` は、そのモジュールの人間向け入口とする。概要、最小例、詳細を読む前に必要な
安全上の警告を持つが、網羅的な API リファレンスにはしない。

## 文書を作成する基準

中央文書は、IDE、XML 文書、TypeScript 宣言、または一つのソースファイルを局所的に読むだけでは十分に
得られない情報を正本として保持する場合に限って作成する。

中央文書に書くもの:

- 複数の構成要素にまたがる責務境界
- 状態の所有者と廃棄条件
- 順序と並行処理に関する保証
- 切断、再接続、再同期、複数クライアント間での挙動
- 外部から観測できる HTTP 契約と SSE 契約
- 使用前に理解する必要がある安全上または運用上の警告

中央文書に書かないもの:

- ファイル、型、メソッド、ビルダー、DOM 要素の網羅的な一覧
- 一つのオプションの意味や既定値
- XML 文書または TypeScript 宣言を読めば得られる API 表
- ソースを順に紹介するだけの案内

一つのオプションの意味は XML 文書が所有する。中央文書には、複数設定間の制約または通信上で観測できる
影響だけを書く。

## 共通の記載規則

`architecture` と `reference` の各文書は、冒頭で次を明示する。

- 文書の目的
- この文書が正本として所有する内容
- 関係する ADR
- 根拠として確認した主要なソース
- この領域を変更する前に読むべき文書

複数箇所にまたがる不変条件には、安定した名前を付け、次のいずれかの証拠を示す。

- 名前を明記した自動テスト
- 強制箇所を明記したソースコード
- 必須の実ブラウザー確認
- 未検証であることを明記した不足箇所

存在しないテストを根拠として記載してはならない。Jint と代用 DOM によるテストを、実ブラウザーテストと
表現してはならない。

## 実施手順

### 第1段階: 退避と失敗した移行の破棄

1. ブランチ、`HEAD`、二つの差分の SHA-256、`git status --short` が「基準状態」と一致することを確認する。
2. `/tmp/duets-documentation-rebuild.<一意な識別子>/` を作業用退避先として作成し、その絶対パスを記録する。
3. 安全のため、現在の staged 差分、unstaged 差分、未追跡ファイルの一覧と内容を退避先の
   `abandoned-migration/` へ保存する。この内容は新文書の根拠に使わない。
4. 基準コミットから、次の三文書を退避先の `baseline-docs/` へ書き出す。
   - `README.md`
   - `docs/architecture.md`
   - `src/Duets.Pad/README.md`
5. 退避した全ファイルについて、元のパス、基準コミット、SHA-256 を記録した一覧を作る。
6. 「破棄対象として想定する既存ファイルの変更」を基準コミットへ戻し、「未コミット追加ファイル」を削除する。
   `git reset --hard`、ブランチ切り替え、履歴変更を使用しない。
7. 実行計画のファイルを除き、作業ツリーと index が基準コミットと一致することを確認する。

### 第2段階: 旧文書を作業ツリーから外す

8. 退避物とハッシュを再確認する。
9. `README.md`、`docs/architecture.md`、`src/Duets.Pad/README.md` を作業ツリーから削除する。
10. 以後、第5段階まで `baseline-docs/` の本文を読まない。

### 第3段階: ADR とソースコードから情報一覧を作る

11. `docs/decisions/index.md` から DuetsPad と全体構造に関係する `Accepted` ADR を特定し、各 ADR を読む。
12. ソースコードから、次の情報を列挙する。
    - `DuetsPadService` が登録するすべての HTTP ルートと認証経路
    - `Protocol/*EventTypes.cs`、`SseSerializer`、送信箇所、ブラウザー受信処理、`DuetsPadEventStream` が扱う
      すべての SSE イベント
    - `SessionRegistry`、`DuetsPadSession`、Canvas、Timeline、Modal、対話操作、入力欄、添付物、Editor の
      状態所有、ロック、廃棄経路
    - ブラウザーの認証情報、投影、再接続、Editor、入力欄、添付物、対話操作の流れ
    - 局所的な契約を所有する公開宣言、XML 文書、TypeScript 宣言
    - 各主張を検証するテストと、実ブラウザーでしか確認できない不足箇所
13. 退避先の `work/claims.md` に、意味単位で次を記録する。

| 項目 | 内容 |
|---|---|
| 識別子 | 作業中に変わらない短い識別子 |
| 主張 | 文書化する情報 |
| ADR 根拠 | 関係する ADR。なければ `None` |
| ソース根拠 | ファイルと型、メソッド、または強制箇所 |
| 検証 | 自動テスト、実ブラウザー確認、または未検証箇所 |
| 所有文書 | この情報を正本として持つ成果物 |

14. ADR とソースコードの不一致を見つけた場合は作業を停止する。

### 第4段階: 白紙から執筆する

15. `work/claims.md` と正本だけを使い、「作成する成果物」に列挙した文書を英語で作成する。

### 第5段階: 旧文書との意味比較

19. 新文書の初稿が完成してから、退避した三つの旧文書を初めて読む。
20. 旧文書の実質的な情報を意味単位へ分解し、退避先の `work/coverage.md` に次のいずれかを記録する。

| 処遇 | 意味 |
|---|---|
| 維持 | 新文書が同じ情報を持つ |
| 言い換え | 意味を変えずに表現を変更した |
| 移転 | 別の成果物が正本になった |
| 宣言へ委譲 | XML 文書または TypeScript 宣言が局所契約を所有する |
| 根拠付きで除外 | ADR またはソースコードが旧記述を否定する |
| 未解決 | 正当な処遇を決められない |

21. 各行に、移転先または除外根拠を記載する。文章の一致、行数、見出し数を判定に使わない。
22. `未解決` が一件でもあれば停止し、利用者の判断を求める。
23. 比較によって見つかった欠落は正本で再確認してから新文書へ反映し、再度比較する。
